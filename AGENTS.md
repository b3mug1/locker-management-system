# Правила разработки

## Назначение

Этот файл содержит обязательные правила для изменений в репозитории системы управления шкафчиками. Правила применяются к backend, frontend, миграциям, конфигурации, документации и автоматизации.

При изменении существующего кода сохраняйте его публичные контракты и стиль, если задача явно не требует обратного. Предпочитайте небольшие проверяемые изменения крупным рефакторингам.

## Общие принципы

- Исправляйте первопричину проблемы, а не только её внешний симптом.
- Перед изменением изучите ближайшую реализацию, вызывающий код и связанные схемы или миграции.
- Не изменяйте несвязанные файлы и не удаляйте пользовательские изменения.
- Не добавляйте зависимости без необходимости. Новая зависимость должна быть оправдана и добавлена в соответствующий manifest.
- Не добавляйте комментарии, которые лишь пересказывают очевидный код. Комментарии нужны для нетривиальных решений и ограничений.
- Ошибки для API должны быть явными и предсказуемыми: используйте корректные HTTP-статусы и существующий формат ответа.
- Не скрывайте ошибки широкими `except Exception`. Если перехват необходим, логируйте причину и сохраняйте корректное состояние транзакции.

## Запрет на использование эмодзи

В данном репозитории строго запрещено использовать любые эмодзи (emoji) в коде, комментариях, строках локализации, логах, интерфейсе пользователя и сообщениях коммитов.

Все статусы, индикаторы и типы приоритетов должны отображаться текстом, CSS или стандартными иконками, но не символами эмодзи.

## Backend

Backend находится в `backend/` и использует FastAPI, SQLAlchemy 2.x async, Pydantic и Alembic.

- Используйте `AsyncSession` и SQLAlchemy 2.x `select()`. Не добавляйте синхронные запросы в async-код.
- Следите за N+1: не выполняйте запросы внутри циклов, если данные можно получить одним `JOIN`, `GROUP BY`, `IN` или `selectinload`.
- Для списков всегда задавайте стабильную сортировку и ограничение `offset/limit` или другой механизм пагинации.
- Выбирайте только необходимые поля для отчётов и аналитики; не загружайте полные ORM-объекты, если нужны только агрегаты или несколько колонок.
- Объединяйте связанные изменения в одну транзакцию. В сервисах используйте `flush()`, когда нужно получить идентификатор до commit; финальный `commit()` должен выполняться на уровне сценария операции.
- Для конкурентных операций, где проверка предшествует записи, используйте транзакционные блокировки или ограничения БД. Одной проверки `SELECT` без блокировки недостаточно.
- Не выполняйте длительные сетевые операции внутри незавершённой транзакции, если это можно избежать.
- Новые изменения схемы оформляйте отдельной миграцией Alembic. Не редактируйте уже применённые миграции.
- Для колонок, участвующих в частых фильтрах, соединениях, сортировке и проверках активных назначений, оценивайте необходимость индекса.
- При изменении API синхронно обновляйте Pydantic-схемы, OpenAPI-контракт и frontend-клиент.

## Импорт данных

- Валидируйте входные данные до записи в базу.
- Для массового импорта избегайте commit, refresh и сетевых операций на каждой строке.
- Обрабатывайте дубли внутри файла и дубли в базе явно, сохраняя понятный отчёт по пропущенным строкам.
- При ошибке транзакции выполняйте rollback до продолжения работы с той же сессией.
- Ограничивайте размер загружаемых файлов и учитывайте потребление памяти при чтении CSV.

## Frontend

Frontend находится в `frontend/` и использует React с Vite.

- Используйте существующие API-модули, контексты, компоненты Layout и локализацию вместо дублирования логики.
- Обрабатывайте состояния загрузки, ошибки, пустые результаты и повторную отправку формы.
- Не храните секреты, пароли или токены в исходниках и публичных переменных сборки.
- Сохраняйте доступность: семантические элементы, клавиатурная навигация, понятные labels и достаточный контраст.
- Не добавляйте визуальные элементы, которые нарушают существующую дизайн-систему или перекрывают содержимое на мобильных экранах.
- Для кнопок действий используйте понятный текст или существующие иконки; не заменяйте смысл интерфейса декоративными символами.

## Безопасность

- Никогда не добавляйте в Git пароли, API-ключи, SMTP-учётные данные, JWT-секреты и другие credentials.
- Используйте переменные окружения и обновляйте `.env.example`, если добавляется новая обязательная настройка.
- Не ослабляйте авторизацию, проверку ролей, валидацию входных данных или защиту от массового доступа без явного требования.
- Не логируйте пароли, токены и полные персональные данные.

## Проверка изменений

Перед завершением задачи:

1. Запустите самый узкий релевантный тест или проверку.
2. Для backend минимум выполните `python -m compileall -q backend/app backend/alembic` и проверьте миграции через Alembic или Docker, если окружение доступно.
3. Для frontend запустите доступные lint, typecheck и build-команды из `frontend/package.json`.
4. Проверьте `git diff --check` и просмотрите итоговый diff.
5. В финальном сообщении укажите выполненные проверки и ограничения окружения.

## Git

- Не используйте `git reset --hard`, `git checkout --` и другие разрушительные команды без прямого запроса.
- Не переписывайте историю и не создавайте коммиты с секретами.
- Сообщения коммитов должны быть короткими, предметными и без эмодзи.
- Перед коммитом убедитесь, что в него не попали несвязанные изменения.
